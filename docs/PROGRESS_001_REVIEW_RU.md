# PROGRESS-001 REVISION — пакет для решения владельца

Статус: проект спецификации, без реализации. [Основной контракт](PROGRESS_001.md). Проверенный master:8503670a31b8adc74bac61b6a84826e6772664eb; PR #10 слит, NAV-CHRONICLE-001 принят владельцем на Windows. Все числа ниже — предложения для рассмотрения, а не утверждённые игровые правила.

## 1. Что уже согласовано

Привычка сохраняет ID при смене имени, ручной иконки, сфер, независимых вкладов 1–10 и будущей частоты. Материал и полученный орнамент постоянны; незавершённая ковка, временное свечение Resonance и отметка выбранной даты независимы. Шесть материалов: Камень → Медь → Бронза → Серебро → Золото → Платина; предпочтительно три этапа детализации каждого. Сферы/вклады не выбирают иконку и не умножают Mastery. Центральная семидневная руна остаётся без изменений.

Из рендера берём качество материалов/детализации и слои состояний. Письменная корректировка важнее чёрно-белых примеров: золотая медаль остаётся золотой без отметки, а зелёная галочка появляется только после успешного сохранения. Иконка в центре оформлена в материале медали; цветные сферы расположены отдельно. Код, схемы, тесты, зависимости и арт в этой задаче не меняются.

## 2. Рекомендованный ритм и ковка

Предлагаю считать завершённые недели понедельник–воскресенье. Условие зачтённого цикла:7 разных дней для ежедневной практики,3 для зала трижды в неделю,1 для еженедельного велозаезда. Любой зачтённый цикл даёт ровно 1 единицу ковки, лишние события/вклады не ускоряют его. Первая неполная неделя не считается; текущая неделя ещё не оценивается. Это календарь подсчёта, без назначения конкретных тренировочных дней.

Сравнены только две модели. A сохраняет материал, но после двух подряд незачтённых недель возвращает незавершённую ковку к началу материала. B дополнительно защищает полученные этапы орнамента. **Рекомендую B:** первая незачтённая неделя удерживает ковку, вторая убирает только хвост после последнего полученного этапа. История, материал и орнамент остаются. Пропуски — отсутствие записанного подтверждения для игрового цикла, не доказательство провала в жизни.

Один пропуск: английский 6/7, зал 2/3 или велосипед 0/1 удерживают прогресс недели, но не дают единицу. Несколько пропусков внутри одной недели всё ещё составляют один незачтённый цикл. После длительного перерыва долг не накапливается. При фронтире 13 и защищённом этапе 12 первая пустая неделя оставляет 13, вторая возвращает 12; следующие ничего не отнимают. Три последующие зачтённые недели дают 13,14,15 — следующий полученный орнамент. Штрафные сообщения и задания «догнать» не нужны.

Ограничение кандидата: регулярные 6/7 дней не продвигают ежедневную привычку. Это необходимо явно одобрить или пересмотреть до реализации; считать их автоматически 7/7 я не предлагаю. Точная допустимость перерывов/сброса пока не утверждена.

## 4. Смена частоты и задние даты

Предлагаю первый явный выбор ритма с сегодняшней даты; последующие изменения — со следующего понедельника. Несколько сохранений для той же будущей даты заменяют одну ожидающую версию; применённые версии не переписываются. Ковка и этап сохраняются, счётчик незачтённых циклов на границе нового ритма очищается. Нельзя переделать старую неделю под более лёгкую частоту или получить несколько единиц за неделю.

Пример: ежедневный ритм с 2 ноября 2026; три полные недели дают Медь 3, четвёртая — фронтир 4.25 ноября выбран 1/неделю,26 ноября изменён на 3/неделю: применяется одна версия с 30 ноября. Записи 30 ноября,2 и 5 декабря дают фронтир 5. Запись задним числом на 24 ноября проверяется по старому ежедневному ритму, но сохраняет сегодняшние имя/сферы/вклады, как текущий журнал. Отмена и повторная запись создают новый eventID, а не вторую единицу за тот же день.

Для уже полученного этапа после исправления старой истории рекомендую сохранять достижение и отметить расхождение основания. Для этого нужен небольшой реестр полученных этапов; накопительный XP-журнал не нужен. Реестр применяется в пересчёте с дат фактического получения, не переносит финальный ранг в начало истории. Это отдельный вопрос одобрения. Уже существующим событиям нельзя выдумывать старую частоту: до явного выбора ритма они остаются журналом/аналитикой без ретроактивной ковки.

Архивные интервалы предлагаю учитывать как нейтральные недели без потери ковки; восстановление возвращает ту же привычку. Из текущего archivedAt нельзя достоверно восстановить старые интервалы архива. Будущий отпуск должен явно приостанавливать ожидания, не создавать выполненные действия. Точные правила требуют решения.

## 5. Resonance и визуальные слои

Предлагаемый свет убывает за два ожидаемых промежутка между практиками: ежедневно 0/1/2 дня дают 1/0,5/0; раз в неделю 0/7/14 дней дают 1/0,5/0. Для 3/неделю промежуток 7/3 дня; на 2-й день свечение 4/7. Это внутренний параметр света, не процент здоровья или Balance. Он зависит от реального сегодня и текущей частоты, галочка — от выбранной даты. Кривая ещё не утверждена.

[Диаграмма независимых слоёв](PROGRESS_001.md#7-visual-contract-and-interaction-composition): постоянная геометрия/материал/этап + выбранная иконка + временный свет + зелёная сохранённая отметка + hover/focus/press. Проверка всех 432 базовых комбинаций, затем архив/ошибка/ожидание/уменьшение движения и реальные контактные листы. Материал нельзя подменять общим серым; hover не означает отметку. Сам рендер сохранён как источник направления в [арт-контракте](art/HABIT_MEDALS.md), без создания картинок в этом PR.

Будущая компактная карточка: основная кнопка на всю полезную область, рядом отдельное меню; никаких вложенных кнопок. Повторное нажатие на отмеченную карточку явно обозначается как отмена; галочка меняется после сохранения. Отдельный Undo/audit не обещается: сегодняшняя отмена физически удаляет событие, повторная запись имеет новый ID/снимки. Ручная галерея небольшая, безопасный старый default — нейтральная печать, не вычисленная из сфер иконка. Финальный набор и удобство отмены требуют визуальной приёмки.

## 6. Данные и резервные копии

Минимальные будущие добавления: версии частоты по habitID/дате, известные интервалы архива, ручной iconID и редкие записи полученных этапов. Даты/имена/сферы/вклады старых событий остаются неизменными; никаких дублированных привычек и переписанных миграций 001–004.

Предлагаемые шаги:005 и backupv 3 для ритма;006/v4 для иконки;007/v5 для этапов, с повторной проверкой свободных номеров перед реализацией. Чистый движок 002A сам по себе не меняет схему. Старыеv1/v2 продолжают импортироваться через строгие адаптеры; новые экспорты/защитные копии содержат все новые поля. Сначала полная проверка и синхронизированная защитная копия, потом одна нативная транзакция замены всех данных. Проверки отказов/аварий должны подтверждать целиком старое или целиком новое состояние. Восстановление старого файла честно заменяет данные его состоянием, не тайно объединяет достижения; предупреждение и защитная копия сохраняются.

Повторные пересчёты/перезапуски/отмена-повторная запись не дают повторный этап. Уникальные будущие награды нуждаются в стабильном смысловом grantID, не одном новом eventID или хеше истории. Реальные рецепты, награды и формулы ресурсов здесь не создаются.
